:::tip[Quick refresher]
Because the dedicated computer vision lessons on Vision Transformer, CLIP, and LLaVA are not yet published, here is the background this lesson uses. A **Vision Transformer** (ViT) slices an image into small non-overlapping squares called **patches**, projects each patch into a vector, and feeds the resulting sequence into a standard Transformer just like a sentence of words. **CLIP** trains an image encoder and a text encoder jointly via **contrastive learning**: across a batch of `(image, caption)` pairs, it pulls matching image and text vectors together and pushes mismatched pairs apart, so CLIP's visual features are already aligned with natural language concepts. On the LLM side, as in [The LLaMA Family](/en/llm/llama-family/), each text token becomes a $D$-dimensional embedding vector, and the Transformer blocks operate purely on that sequence of vectors. To let an LLM "see" an image, we turn the image into a sequence of $D$-dimensional vectors and feed them in alongside the text tokens—the core idea of LLaVA.
:::

## Intuition

### LLMs only read sequences of vectors

In [Image and Video Generation APIs](/en/llm/image-video-api/), you sent an image alongside a question and the model answered "there is a red square in the center". That lesson noted that the provider converts the image into visual tokens under the hood. This lesson opens that box.

Each type of data (text, image, audio, video) is called a **modality**; a model that processes multiple modalities is **multimodal**.

Here is the key insight: a Transformer block does not care where its input vectors came from. It takes a sequence of $D$-dimensional vectors and outputs a sequence of $D$-dimensional vectors. If you can turn an image into a sequence of $D$-dimensional vectors that describe its contents, a Transformer can read them right away.

Picture a jigsaw puzzle. Slice an image into a regular grid of squares and read the squares left to right, top to bottom, like words on a page. Each square is a "word", and the whole image becomes a "sentence": a $224 \times 224$ image cut into $16 \times 16$ squares yields a 196-word sentence. That is a Vision Transformer (ViT).

### Two jobs and a translator

First, each square's vector must carry **high-level meaning**: if a patch shows a cat's ear, its vector should encode "cat ear", not just raw RGB pixel values. That is the job of a pre-trained vision encoder, most commonly taken from CLIP.

Second, because the vision encoder and the LLM were trained separately, they "speak different languages": the vision encoder outputs $D_v$-dimensional vectors in its own feature space, whereas the LLM expects $D$-dimensional vectors in its token embedding space. We need a lightweight **translator** in the middle: the **projector**.

Once we have visual vectors, how do we hand them to the LLM? Think of three ways to give illustrations to someone reading a book:

- **Paste the pictures right onto the pages**, inline with the text: simple, though the pictures take up page space. That is LLaVA's sequence concatenation approach.
- **Lay the pictures on the desk next to the book**, letting the reader glance over every few paragraphs: the book itself stays the same length, though the reader needs extra "side-glancing" machinery. That is the cross-attention approach of Llama 3.2 Vision.
- **Write both pictures and words in a single shared alphabet** from day one, so a single reader can both read and write either modality seamlessly. That is Chameleon.

The problem of this lesson is: **how do we convert an image into a sequence of vectors that speak the same "language" as an LLM's token embeddings, where do we plug those vectors in, and which weights do we train so the LLM can answer questions about images without forgetting how to read text?**

## Theory

### Notation

An input image has height $H$, width $W$ (in pixels), and $C$ color channels ($C = 3$ for RGB). Note that in this lesson $H$ denotes image height, not the number of attention heads as in the LLaMA lesson; similarly, the italic scalar $W$ (width) is distinct from the bold projection matrix $\mathbf{W}$ in Step 4, and $H$ is distinct from the visual hidden matrix $\mathbf{H}_v$. Each square patch has side length $P$, giving $N$ patches per image. The vision encoder outputs vectors of dimension $D_v$, the LLM uses embedding dimension $D$, and the combined sequence read by the LLM has length $L$.

### Step 1: slicing an image into patches

Divide the image into non-overlapping $P \times P$ squares. Vertically there are $H/P$ rows of patches, and horizontally there are $W/P$ columns of patches, so the total number of patches is their product:

$$
N = \frac{H}{P} \cdot \frac{W}{P} = \frac{HW}{P^2}
$$

This requires $H$ and $W$ to be divisible by $P$ (if not, the image is resized, cropped, or padded first). Each patch contains $P \cdot P$ pixels with $C$ channels per pixel, so flattening a patch yields a row vector $\mathbf{x}_i \in \mathbb{R}^{P^2 C}$.

Notice that $P$ sits in the denominator and is squared: **halving the patch size $P$—or doubling both image dimensions $H$ and $W$—quadruples the number of image tokens $N$**.

### Step 2: patch embedding

Each flattened patch is multiplied by **a single shared** learnable matrix $\mathbf{E}$, and then a position vector is added:

$$
\mathbf{z}_i = \mathbf{x}_i\,\mathbf{E} + \mathbf{p}_i,
\qquad
\mathbf{E} \in \mathbb{R}^{(P^2 C) \times D_v}
$$

Here $\mathbf{x}_i$ is the row vector of patch $i$, $\mathbf{z}_i \in \mathbb{R}^{D_v}$ is the resulting patch token, and $\mathbf{p}_i$ is the learnable **position embedding** for slot $i$ (playing the exact same role as positional vectors in [Build Your First LLM](/en/llm/build-first-llm/)).

Why use a single shared matrix $\mathbf{E}$ for every patch? For the same reason a text LLM uses a single token embedding table across all sequence positions: the word "cat" maps to the same base vector whether it appears at the start or end of a sentence. Consequently, two identical patches at opposite corners of an image produce the exact same $\mathbf{x}_i\mathbf{E}$ (as our NumPy cell verifies), making $\mathbf{p}_i$ essential for telling spatial locations apart. ViT numbers patches in raster order and uses standard 1D learnable position embeddings; Dosovitskiy et al. tested 2D-aware position embeddings and found no significant gain. ViT also prepends a learnable **class token** (like BERT's `[CLS]`) and runs the sequence through a stack of standard Transformer encoder blocks. Beyond the initial patch slicing, ViT bakes in almost no image-specific inductive bias—spatial relationships are learned entirely from data via self-attention.

In code, "slice into non-overlapping $P \times P$ patches and multiply each by $\mathbf{E}$" is mathematically identical to a 2D **convolution** (`nn.Conv2d`) with kernel size $P \times P$ and stride $P$. Passing the embedded patches through the vision encoder produces $\mathbf{Z}_v \in \mathbb{R}^{N \times D_v}$, where each row is a context-enriched feature vector for one patch.

### Step 3: why start from a CLIP vision encoder

CLIP (Radford et al., 2021) was trained on 400 million `(image, text)` pairs collected from the internet. Given a batch of $N_b$ pairs, CLIP computes the cosine similarity between all $N_b$ image embeddings and all $N_b$ text embeddings to form an $N_b \times N_b$ similarity matrix whose main diagonal holds the true pairs, then minimizes symmetric cross-entropy across rows and columns to maximize diagonal scores relative to off-diagonal mismatches. Because CLIP's visual features were trained directly to align with natural language descriptions, they provide a head start for connecting to an LLM. LLaVA uses CLIP's pre-trained ViT-L/14 encoder ($14 \times 14$ patches). Keep in mind that CLIP itself only **scores** image–text similarity; it cannot generate text.

### Step 4: the projector and the LLM input sequence

The original LLaVA (Liu et al., 2023) bridges the vision encoder to the LLM using a single linear projection matrix:

$$
\mathbf{H}_v = \mathbf{Z}_v\,\mathbf{W},
\qquad
\mathbf{W} \in \mathbb{R}^{D_v \times D}
$$

Each $D_v$-dimensional row of $\mathbf{Z}_v$ is mapped to a $D$-dimensional row matching the LLM's token embedding dimension. (The paper writes $\mathbf{H}_v = \mathbf{W}\mathbf{Z}_v$ using column vectors; we use row vectors to match standard PyTorch tensor shapes `(batch, N, D)`.) The authors intentionally chose a simple linear layer for rapid prototyping. LLaVA-1.5 (Liu et al., 2023) upgraded the projector to a **two-layer MLP** and reported stronger multimodal alignment:

$$
\mathbf{H}_v = \phi\big(\mathbf{Z}_v\,\mathbf{W}_1 + \mathbf{b}_1\big)\,\mathbf{W}_2 + \mathbf{b}_2
$$

where $\phi$ is a non-linear **activation function**. While the paper simply refers to a "two-layer MLP", the official LLaVA-1.5 codebase uses GELU (`mlp2x_gelu`: Linear $\to$ GELU $\to$ Linear), which we follow in our PyTorch example.

In the simplest layout (and in our code), the projected visual tokens $\mathbf{H}_v$ are concatenated right in front of the text token embeddings $\mathbf{H}_t$ to form a single unified sequence:

$$
\begin{bmatrix} \mathbf{H}_v \\ \mathbf{H}_t \end{bmatrix}
\in \mathbb{R}^{L \times D},
\qquad
L = N + L_{\text{text}}
$$

Here $\mathbf{H}_t$ has $L_{\text{text}}$ rows corresponding to the text prompt tokens. (During training, LLaVA randomly places the image either before or after the first user question.) From this point onward, the LLM runs as usual, autoregressively predicting the next token, with the cross-entropy training loss computed only on the assistant's answer tokens.

**Image token count is a real compute and memory cost.** Because self-attention scores all pairs of positions in the sequence, its work scales as $L^2$. A 50-token text question paired with 576 image tokens produces a sequence of length $626$, requiring $626^2 \approx 392\,000$ attention pairs per head per layer—compared to just $50^2 = 2\,500$ for text alone. Every image token also occupies a slot in the context window and adds an entry to the KV cache.

| Image resolution $H \times W$ | Patch size $P$ | Image tokens $N$ | Where it appears |
|---|---:|---:|---|
| $224 \times 224$ | 16 | 196 | ViT-B/16 in the original ViT paper |
| $224 \times 224$ | 14 | 256 | CLIP ViT-L/14 at 224px; also the base patch count in the Llama 3 vision experiments |
| $336 \times 336$ | 14 | 576 | CLIP ViT-L/14 at 336px, used in LLaVA-1.5 |
| $448 \times 448$ | 14 | $1\,024$ | Doubling both sides of the 224px / $P=14$ setup quadruples $N$ |

### LLaVA's two-stage training

| Stage | Training data | Vision encoder | Projector | LLM |
|---|---|---|---|---|
| 1. Feature alignment | 595K filtered image–caption pairs from CC3M (Conceptual Captions) | Frozen | Trainable | Frozen |
| 2. End-to-end instruction tuning | LLaVA-Instruct-158K: multi-turn conversation, detailed description, complex reasoning | Frozen | Trainable | Trainable |

**Stage 1: pre-training for feature alignment.** Each image–caption pair is formatted as a single-turn conversation ("Describe this image briefly" $\to$ original caption). Only the projector weights are updated. The authors describe this as training a compatible "visual tokenizer" for the frozen LLM: teaching the translator while holding both endpoints fixed.

**Stage 2: visual instruction tuning.** The vision encoder stays frozen, while both the projector and the LLM (Vicuna) are updated on multimodal instruction-following data. This extends the **instruction tuning** paradigm from [GPT Family and Multi-Task Fine-Tuning](/en/llm/gpt-family-finetuning/) to vision. Remarkably, the 158K examples in LLaVA-Instruct were generated by **text-only GPT-4**, which was fed human captions and object bounding-box coordinates as symbolic text and asked to write rich Q&A pairs about the scene.

LLaVA-1.5 keeps this exact two-stage schedule, upgrading to the two-layer MLP projector, $336 \times 336$ input resolution, and additional academic VQA datasets in Stage 2.

### Cross-attention: Llama 3.2 Vision

Whereas LLaVA splices visual tokens **into** the main token sequence, cross-attention keeps the image **on the side**. Let $\mathbf{X} \in \mathbb{R}^{L \times D}$ be the text token representations at a given layer of the LLM, and let $\mathbf{Z} \in \mathbb{R}^{N \times D_v}$ be the encoded visual features. A cross-attention layer computes:

$$
\begin{aligned}
\mathbf{Q} &= \mathbf{X}\mathbf{W}_Q, \quad \mathbf{K} = \mathbf{Z}\mathbf{W}_K, \quad \mathbf{V} = \mathbf{Z}\mathbf{W}_V \\
\mathrm{CrossAttn}(\mathbf{X}, \mathbf{Z}) &= \mathrm{softmax}\!\left(\frac{\mathbf{Q}\mathbf{K}^\top}{\sqrt{d}}\right)\mathbf{V}
\end{aligned}
$$

Queries come from the text tokens, while keys and values come from the image patches (exactly like the encoder–decoder cross-attention in [Sequence-to-Sequence Models](/en/llm/seq2seq/)); $d$ is the per-head dimension. The attention score matrix has shape $L \times N$: each text token attends across all $N$ image patches. The output has $L$ rows—matching the text length—so the main sequence never grows by a single token.

Let's keep three primary sources clear:

- **The Llama 3 paper, Section 7** (Grattafiori et al., 2024) describes **vision experiments** that were still under development at the time. They used a ViT-H/14 vision encoder (630M parameters, contrastively pre-trained on 2.5B image–text pairs at $224 \times 224$ resolution = 256 patches, and scaled to up to four $336 \times 336$ tiles during adapter training). Cross-attention layers were inserted after every fourth self-attention layer of the LLM (adding ~100B parameters on the 405B model). During adapter training, the authors updated the vision encoder and cross-attention layers while **intentionally keeping the base LLM parameters frozen** (Sections 1 and 7).
- **The Llama 3.2 Vision model card** (Meta, released September 25, 2024) documents the released 11B and 90B models: built on top of text-only Llama 3.1 by adding a separately trained set of cross-attention image adapter layers, pre-trained on 6 billion image–text pairs.
- **Meta's Llama 3.2 release post** (September 25, 2024) confirms for the released models that training updated the image encoder and adapter weights while intentionally freezing the language-model parameters, so text-only capabilities remain completely unchanged and the Vision models serve as a drop-in replacement for Llama 3.1.

The Llama 3 paper highlights four advantages of this design: vision and language teams can develop independently; it avoids the complexities of joint multimodal pre-training; text-only performance is **guaranteed not to regress** because the LLM backbone is untouched; and high-resolution image tokens never pass through the heavy FFN layers of the main LLM, saving compute.

### Early fusion: Chameleon

Chameleon (Chameleon Team, 2024) takes the opposite philosophical extreme: no separate vision encoder at all. Instead, a learned image tokenizer **quantizes** a $512 \times 512$ image into $1\,024$ discrete tokens (vector quantization into a discrete **codebook** of $8\,192$ visual codes, distinct from weight quantization in the PEFT lesson). Those $8\,192$ image token IDs live directly inside a single shared vocabulary of $65\,536$ tokens alongside BPE text tokens. A single decoder-only Transformer is trained **from scratch** with next-token prediction over interleaved text and image tokens, enabling it to both **read and generate** images and text in any order. The authors call this **early fusion**, in contrast to **late-fusion** models that bolt a separate modality encoder onto an LLM, such as Flamingo (Alayrac et al., 2022) or LLaVA. The trade-offs noted by the authors: end-to-end mixed-modal training requires careful architectural stabilization to prevent divergence, and discrete image tokenizers struggle with heavy OCR / small text inside images.

:::note[Key takeaway]
An image becomes $N = HW/P^2$ patch tokens; a projector maps their dimension $D_v \to D$. LLaVA concatenates projected image tokens directly into the LLM input sequence, Llama 3.2 Vision lets text tokens attend to image features from the side via cross-attention while keeping the base LLM frozen, and Chameleon discretizes images into the same vocabulary as text from scratch.
:::

## Common pitfalls

:::caution[Thinking the LLM "sees" raw pixels, or that the projector translates images into English words]
The LLM only ever sees the sequence of feature vectors emitted by the vision encoder; any visual detail discarded by the vision encoder is gone forever. The Llama 3 report notes that contrastive vision encoders often lose fine-grained spatial localization, and the Chameleon paper notes that discrete image tokenizers struggle with dense text inside images. Nor does the projector output discrete words—it maps continuous vectors from $\mathbb{R}^{D_v}$ to $\mathbb{R}^{D}$. Always verify model answers carefully on tasks involving tiny text (OCR), fine spatial counting, or subtle visual details.
:::

:::caution[Confusing patch size P with patch count N, or assuming higher resolution is free]
A smaller patch size $P$ means a **larger** token count $N$: halving $P$ or doubling image height and width quadruples $N$ and increases self-attention pairs among image tokens by $16\times$. Higher resolution helps the model read small details, but directly consumes context length, KV cache memory, and API token billing. Also remember that most pre-trained vision encoders expect a fixed base resolution (such as $336 \times 336$ in LLaVA-1.5), resizing or tiling larger images to fit.
:::

:::caution[Mixing up which modules are frozen across architectures]
LLaVA **freezes the vision encoder**, training the projector in Stage 1 and the projector + LLM in Stage 2. The Llama 3 vision experiments and the released Llama 3.2 Vision models do the opposite: they **freeze the base LLM**, training the vision encoder and cross-attention adapters so text-only capabilities never regress. Also keep experimental details separate from production releases: specifics like "cross-attention after every fourth layer" and ViT-H/14 come from Section 7 of the Llama 3 paper (vision experiments), whereas the Llama 3.2 Vision model card does not disclose every internal layer count. Finally, always check language support in the model card: the Llama 3.2 Vision model card notes that while text-only supports eight languages, **image+text tasks are officially supported in English only**.

## Summary and further reading

**Key takeaways:**

- LLMs operate on sequences of vectors. A Vision Transformer slices an image into $N = HW/P^2$ patches, projects each patch with a shared matrix $\mathbf{E}$, and adds position embeddings $\mathbf{p}_i$. Image token count $N$ is a real runtime cost: it consumes context window slots and scales self-attention pairs as $O(L^2)$.
- The standard multimodal blueprint connects Vision Encoder (often from CLIP) $\to$ Projector ($D_v \to D$) $\to$ LLM. LLaVA concatenates visual tokens directly into the sequence ($L = N + L_{\text{text}}$) and trains in two stages: projector-only alignment first, followed by joint projector + LLM visual instruction tuning, keeping the vision encoder frozen throughout.
- Llama 3.2 Vision injects visual features via cross-attention layers (queries from text, keys and values from image patches), leaving text sequence length unchanged and keeping the base LLM frozen so text-only performance is preserved.
- Chameleon quantizes images into discrete codebook tokens inside a single shared vocabulary ($1\,024$ tokens per $512 \times 512$ image) and trains a unified Transformer from scratch to both read and generate interleaved text and images.
