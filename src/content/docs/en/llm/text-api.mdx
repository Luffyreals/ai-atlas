## Intuition

Suppose you want your Python program to answer questions, summarize text, or extract structured details from customer reviews. You do not need to train a model yourself: providers like OpenAI, Google, and Groq already run LLMs on their servers. Your program sends text over the network to their **API** (application programming interface) and receives the text generated by the model. AI Atlas divides working with LLMs into four levels: calling an existing model via an API, building prompts/RAG/agents on top of an existing model, fine-tuning, and pre-training from scratch. This lesson starts at the first level.

Try calling the API a few times and you will notice three surprising things:

- **The model forgets immediately.** You ask "What is a token?", and then follow up with "Give an example". If your second call only sends the second sentence, the model has no idea what "an example" refers to. It is like texting someone who loses their memory after every reply: you have to paste the entire conversation history into every new message.
- **Same question, different answer each time.** The model writes one piece of text at a time, and each piece is **randomly sampled** from a probability distribution. Specific parameters let you dial that randomness up or down.
- **You pay by the piece of text.** Those pieces are called **tokens**. Providers charge and enforce limits by token count, counting both the tokens you send in and the tokens the model writes out.

The problem this lesson solves is: **send the exact context the model needs over the API, understand how the model picks each token and which parameters control that choice, and write code that survives network glitches, rate limits, and malformed outputs.**

## Theory

### A single API call

This lesson uses the `openai` Python library—an **SDK** (software development kit provided by the vendor)—and the **Chat Completions** endpoint (an endpoint is a specific API address that performs a specific action). OpenAI recommends the Responses API for new applications, but continues to support Chat Completions long-term, and Gemini, Groq, and Ollama all offer this exact OpenAI-compatible endpoint. By changing only the address (`base_url`), API key, and model name, the exact same code runs across multiple providers.

A single call sends two main pieces of data: the model name and a `messages` list. Each item in `messages` has a **role** and content:

| Role | Written by | Purpose |
|---|---|---|
| `system` | You, the developer | Sets the persona, tone, and rules: "You are a teaching assistant. Answer briefly." Called the **system prompt** |
| `user` | The end user | Questions or requests |
| `assistant` | The model, in earlier turns | Previous replies from the model, sent back so the model "remembers" |

In the two-turn conversation from the second code example, the second turn sends the following list:

| Role | Content |
|---|---|
| `system` | You are a teaching assistant. Answer briefly in English. |
| `user` | What is a token in a language model? Answer in two sentences. |
| `assistant` | (the reply from turn one, saved by your program) |
| `user` | Give an example with an English sentence. |

Thanks to the first three rows, "Give an example" makes sense. The API is **stateless**: the server stores nothing between calls, so everything the model needs to know must be included in `messages`.

For newer models, OpenAI renames the `system` role to `developer`, but Gemini, Groq, and Ollama still use `system`, so the code in this lesson uses `system`.

There are three fields in the response you will read most often: `choices[0].message.content` holds the text the model wrote; `choices[0].finish_reason` tells you why the model stopped (`"stop"` when it finished naturally, `"length"` when it hit the token ceiling); and `usage` reports the input and output token counts.

### Tokens and cost

A **token** is the unit of text a model reads and writes. It is neither strictly a word nor a character: a common word may be a single token, while a rare word is split into several tokens. Every model has a **context window**: the maximum total number of input plus output tokens allowed in a single call.

Providers charge per token, usually with two separate prices: **input tokens** (the prompt, including conversation history) and **output tokens** (the completion). Because history is resent on every turn, the cost of a long conversation grows faster than you might expect. Let $s$ be the number of tokens in the system prompt, $q$ the tokens in each question, and $a$ the tokens in each answer. On turn $r$, you send the system prompt, $r - 1$ earlier turns (each containing one question and one answer), and the new question. Let $N_r$ be the number of input tokens on this turn:

$$
N_r = s + (r - 1)(q + a) + q
$$

Now sum from turn 1 to turn $R$. The terms $s$ and $q$ each appear $R$ times. The middle term requires summing $0 + 1 + \dots + (R - 1) = \frac{R(R - 1)}{2}$:

$$
\sum_{r=1}^{R} N_r = R(s + q) + (q + a)\,\frac{R(R - 1)}{2}
$$

The final term contains $R^2$: total input tokens grow **quadratically** with the number of turns. With $s = 20$ and $q = a = 50$: turn 1 sends 70 tokens, turn 10 sends 970 tokens, and all 10 turns combined send $10 \cdot 70 + 100 \cdot 45 = 5200$ input tokens. That is why production chatbots trim or summarize older history.

**The `max_tokens` parameter** sets a ceiling on how many tokens the model may write in a single call. This cap limits cost, but it **does not** make the model write more concisely: if the model hits the ceiling, its sentence is cut off mid-thought and `finish_reason` becomes `"length"`. If you want a short answer, ask for it in the prompt. OpenAI has renamed this parameter to `max_completion_tokens`, which also counts the hidden reasoning tokens of **reasoning models** (models that think through multiple internal steps before answering). Ollama only lists the old name; OpenAI and Groq still accept the old name as deprecated (though OpenAI's reasoning models reject it). For broad compatibility, the code in this lesson omits this cap and lets the provider use its default.

### How the model chooses the next token

An LLM generates text one token at a time. At each step, it reads all preceding tokens and outputs one raw score for **every** token in its vocabulary, called a **logit**. Let the vocabulary be $\mathcal{V}$ with $V$ tokens, and let the logit of token $i$ be $z_i$. The larger the logit, the better that token fits as the next token according to the model.

For example, after the prompt "The weather today is very", suppose the model only considers 10 candidates (for simplicity, treat each word as a single token):

| Token | nice | hot | cold | cool | sunny | humid | clear | windy | wet | dark |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Logit $z_i$ | 3.0 | 2.6 | 2.0 | 1.5 | 1.1 | 0.6 | 0.1 | −0.4 | −1.0 | −1.6 |

**Step 1: turn logits into probabilities with softmax.** Logits can be negative and do not sum to 1, so they are not probabilities yet. The **softmax** function takes $\exp$ of each logit (making it strictly positive) and divides by the sum (so the results add up to 1):

$$
p_i = \frac{\exp(z_i)}{\sum_{j=1}^{V} \exp(z_j)}
$$

**Step 2: divide logits by temperature $T$ before softmax.** This is the `temperature` knob:

$$
p_i(T) = \frac{\exp(z_i / T)}{\sum_{j=1}^{V} \exp(z_j / T)}, \qquad T > 0
$$

Setting $T = 1$ recovers the standard softmax from Step 1. To see what $T$ does, compare the probabilities of two tokens $i$ and $j$. Because both fractions share the same denominator, the denominators cancel, and $\exp(x) / \exp(y) = \exp(x - y)$ gives:

$$
\frac{p_i(T)}{p_j(T)} = \frac{\exp(z_i / T)}{\exp(z_j / T)} = \exp\!\left(\frac{z_i - z_j}{T}\right)
$$

This formula reveals three properties:

- **The ranking never changes.** If $z_i > z_j$, the ratio is greater than 1 for every $T > 0$. Temperature never promotes a lower-ranked token above a higher-ranked one.
- **$T < 1$ amplifies differences, making the distribution sharper.** The tokens "nice" and "hot" differ by 0.4 logits. At $T = 1$, "nice" is $e^{0.4} \approx 1.49$ times as likely as "hot"; at $T = 0.5$, it is $e^{0.8} \approx 2.23$ times as likely. As $T \to 0$, the token with the largest logit takes nearly all the probability mass: the model almost always picks it, which is called **greedy decoding**.
- **$T > 1$ shrinks differences, making the distribution flatter.** Rare tokens get a bigger chance: replies become more varied, but also more likely to drift off topic.

For the 10 logits above (numbers from the first code cell):

| $T$ | nice | hot | cold | Top-p 0.9 keeps |
|---:|---:|---:|---:|---:|
| 0.5 | 0.599 | 0.269 | 0.081 | 3 tokens |
| 1 | 0.382 | 0.256 | 0.140 | 5 tokens |
| 1.5 | 0.286 | 0.219 | 0.147 | 7 tokens |

**Step 3 (optional): trim the tail with top-k.** A real vocabulary has tens or hundreds of thousands of tokens. Each token in the long tail has a tiny probability, but together the tail can add up to a noticeable sum, so every now and then a nonsensical token gets drawn. **Top-k** keeps only the $k$ most probable tokens (the set $\mathcal{V}_k$), sets all other tokens to probability 0, and **renormalizes** so the kept probabilities sum to 1:

$$
p_i^{(k)} =
\begin{cases}
\dfrac{p_i}{\sum_{j \in \mathcal{V}_k} p_j}, & i \in \mathcal{V}_k \\[6pt]
0, & i \notin \mathcal{V}_k
\end{cases}
$$

With $k = 3$ at $T = 1$: the top three tokens sum to $0.382 + 0.256 + 0.140 = 0.778$; dividing each by this sum gives $0.491$, $0.329$, and $0.180$.

**Step 3' (optional): trim the tail with top-p.** Holtzman et al. (2020) proposed this method after observing that both extremes fail: always picking the most likely token produces flat, repetitive text, whereas sampling from the full vocabulary occasionally wanders into the nonsensical tail. Top-k cuts off the tail, but $k$ is fixed: when the model is very certain, $k = 3$ still keeps two nearly absurd tokens; when the model is torn between dozens of reasonable choices, $k = 3$ throws almost all of them away. **Top-p**, also called **nucleus sampling**, sorts tokens by decreasing probability and takes the **smallest set** $\mathcal{V}_p$ whose cumulative probability meets or exceeds the threshold $p$:

$$
\sum_{i \in \mathcal{V}_p} p_i \ \ge\ p
$$

and then renormalizes just like top-k (note that the threshold $p$ has no subscript, unlike the individual token probabilities $p_i$). At $T = 1$, the cumulative sums are $0.382$; $0.638$; $0.778$; $0.864$; $0.921$. The first four tokens only reach $0.864 < 0.9$, so the fifth token must be included: top-p $0.9$ keeps 5 tokens. The table above shows that the same $0.9$ threshold keeps 3, 5, or 7 tokens depending on how sharp the distribution is. The kept set **adapts**: fewer tokens when the model is confident, more tokens when it is uncertain.

**Step 4: sample one token** from the final distribution, append it to the text, and repeat from the beginning for the next token.

:::note[Key takeaway]
Logits → divide by $T$ → softmax → (top-k or top-p trims the tail and renormalizes) → sample one token. $T$ never changes the token ranking, only the sharpness: small $T$ makes the distribution sharp and close to picking the top token; large $T$ makes it flat and more diverse. Top-k keeps a fixed number of tokens; top-p keeps a dynamic number of tokens based on the model's certainty.
:::

**In the API.** Chat Completions supports `temperature` (from 0 to 2 on OpenAI) and `top_p`, but **not** `top_k`. OpenAI recommends tuning one or the other, not both, since both reshape the distribution and their combined effect is hard to predict. Setting `temperature=0` is well suited for information extraction, though it does not guarantee identical output on every run: OpenAI notes that determinism is not guaranteed, and Groq internally converts `0` to `1e-8`.

### Streaming

Because the model generates one token at a time, you do not have to wait for the entire reply before displaying it. When you set `stream=True`, the API yields a sequence of **chunks** over time, each carrying a few new tokens in `choices[0].delta.content`. Total generation time is nearly the same, but the first words appear almost immediately instead of several seconds later. The snippet below reuses `client`, `MODEL`, and `messages` from the conversation example in the Code examples section:

```python
stream = client.chat.completions.create(model=MODEL, messages=messages,
                                        stream=True)
for chunk in stream:
    # empty choices: usage chunk (when include_usage is on), or on some providers
    if not chunk.choices:
        continue
    text = chunk.choices[0].delta.content
    if text:  # the first and last chunks may carry no text
        print(text, end="", flush=True)  # flush: print right away, do not buffer
```

If you need token counts while streaming, pass `stream_options={"include_usage": True}`: the token usage arrives in a final chunk whose `choices` list is empty, and if the stream drops mid-way you may never receive that chunk. The SDK also **does not automatically retry** an interrupted stream: whatever chunks you already received remain partial.

### Errors, rate limits, and retries

Any call over a network can fail. All exceptions raised by the SDK inherit from `openai.APIError`. Here are the ones you will encounter most often:

| HTTP status | Exception class | Common cause | Retried by SDK? |
|---|---|---|---|
| — | `APIConnectionError` (subclass `APITimeoutError`) | Could not reach the server, or the request timed out | Yes |
| 400 | `BadRequestError` | Invalid request, such as a parameter the provider does not support | No |
| 401 | `AuthenticationError` | Wrong or missing API key, or a key for a different provider | No |
| 403 | `PermissionDeniedError` | Your key does not have access to that model or feature | No |
| 404 | `NotFoundError` | Wrong model name or wrong `base_url` | No |
| 429 | `RateLimitError` | Exceeded a **rate limit** (requests or tokens per minute/day) | Yes |
| ≥ 500 | `InternalServerError` | Server-side failure | Yes |

Every error with an HTTP status code inherits from `APIStatusError` and exposes a `status_code` attribute. The SDK also retries two less common status codes: 408 (request timeout) and 409 (conflict). The general rule is: **only retry transient errors** (network failures, 408, 409, 429, ≥ 500). Errors 400–404 mean the request itself is broken, so retrying will fail every time.

Retrying immediately is usually counterproductive because an overloaded server will only get more overloaded. The standard solution is **exponential backoff**: double the wait time after each failure, cap it at a maximum, and subtract a random offset called **jitter** so that many clients failing at the same moment do not all knock on the server's door in lockstep. In `openai` 3.37, the SDK waits roughly 0.5, 1, 2, 4, and up to 8 seconds between attempts, applies up to 25% random jitter, and honors the server's `Retry-After` response header if present (unless it exceeds 120 seconds, in which case it raises immediately).

You do not need to write this retry loop yourself. `OpenAI(max_retries=...)` sets the maximum number of retries (default 2; set 0 to disable), and `OpenAI(timeout=...)` sets the per-call timeout (default 10 minutes).

### JSON output

When your program needs to process the model's answer, you usually want structured data such as JSON rather than free-form prose. There are three levels of enforcement, from loose to strict:

1. **Prompt instruction only:** "Return only a JSON object with two keys…". Easiest to use, but the model occasionally adds conversational filler or wraps the JSON in a Markdown code block.
2. **JSON mode:** `response_format={"type": "json_object"}` guarantees that the returned string is valid JSON, but **does not** guarantee that it contains the exact keys you asked for. You must still describe the desired keys in the prompt, and the word "JSON" must appear somewhere in `messages` (OpenAI returns an error if it is missing).
3. **Structured outputs:** `{"type": "json_schema", ...}` guarantees that the output matches a provided schema when `strict` is enabled. OpenAI recommends this whenever the model supports it.

Support varies across providers, and JSON output can still be truncated mid-string if the response hits the token ceiling. Therefore, regardless of which level you use, always parse the result with `json.loads` inside a `try`/`except` block.

### Limitations

- **Each "OpenAI-compatible" provider omits certain features.** Sending an unsupported field may be silently ignored or trigger a 400 error (see the provider table in Code examples).
- **Replies can be dead wrong while sounding completely confident.** The [Prompt Engineering](/en/llm/prompt-engineering/) and [RAG and Modern Chatbots](/en/llm/rag-chatbot/) lessons cover ways to reduce this.
- **The code here runs in the command line.** Streaming replies to a web interface is covered in [Building UIs with Gradio and Streamlit](/en/llm/gradio-streamlit/).
- **This lesson treats logits as given.** [Building Your First LLM](/en/llm/build-first-llm/) builds a small model from scratch and shows how logits are computed.

Try adding `max_tokens=20` to the call to trigger `length`: the reply gets cut off mid-sentence. ## Common pitfalls

:::caution[Hardcoding API keys in source files and pushing to Git]
A key written in your code travels with every copy of the file: chat messages to friends, public Git repositories, even screenshots. Automated bots continuously scan GitHub for leaked keys and spend your credits within seconds. Always read keys from environment variables as shown in this lesson. If you ever leak a key, log into your provider's dashboard immediately to revoke it and generate a new one; deleting the Git commit is not enough, because the key may already have been scraped and still lives in commit history, forks, or caches.
:::

:::caution[Assuming the API remembers the conversation]
If you only send the newest question, the model treats you like a stranger on every turn. You must maintain the `messages` list yourself and resend the entire list on each call. Consequently, input tokens, cost, and latency grow with history length, and once the history exceeds the context window, the request fails. Long conversations need a strategy to trim or summarize older turns.
:::

:::caution[Retrying every error, or stacking your own retry loop on top of the SDK]
Errors 400, 401, 403, and 404 never fix themselves; retrying them only wastes time and quota. A 429 error caused by an exhausted billing balance or spending cap will not resolve by waiting either, even though the SDK retries it like any other 429. For genuine transient errors, the SDK already retries twice with exponential backoff. If you wrap the call in your own 5-attempt `for` loop without setting `max_retries=0`, a single failure can balloon into 15 requests, making rate-limit trouble much worse.
:::

## Summary and further reading

**Key takeaways:**

- Calling an LLM means sending `model` and a `messages` list (`system`, `user`, `assistant` roles) to an API. Because the API is stateless, you resend the conversation history on every turn, and cumulative input tokens grow quadratically with the number of turns. Inspect `content`, `finish_reason`, and `usage` in the response.
- The model outputs a logit $z_i$ for each token; probabilities are $p_i(T) = \exp(z_i/T) / \sum_j \exp(z_j/T)$. Smaller $T$ sharpens the distribution, larger $T$ flattens it, and the token ranking never changes. Top-k keeps $k$ tokens, while top-p keeps the smallest set with cumulative probability $\ge p$, before renormalizing and sampling. OpenAI-compatible APIs expose `temperature` and `top_p`, not `top_k`.
- `max_tokens` is a cost ceiling, not a conciseness knob. `stream=True` yields text incrementally; interrupted streams are not automatically retried.
- Only retry transient errors (network, 408, 409, 429, ≥ 500) using exponential backoff with jitter, which the SDK handles via `max_retries`. Always parse JSON output with `json.loads` inside `try`/`except`, and keep API keys in environment variables.
