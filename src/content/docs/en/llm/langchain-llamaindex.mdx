## Intuition

Your RAG chatbot is working great: around 40 lines of Python, the `openai` SDK, and a NumPy array acting as a vector store. Then new requirements start pouring in. The documents are now 200 PDF files, a handful of web pages, and a folder of Word files. An in-RAM vector store is no longer enough; you need a real vector database. Your team wants to try another provider without rewriting the code. And when the chatbot gives a wrong answer, you want to inspect which chunks it retrieved and what the exact prompt sent to the model looked like.

Every one of those requirements can be coded by hand. But if you build them all, you are essentially writing your own library: a PDF reader, a sentence-aware chunk splitter, wrapper classes for each vector store, and a step-by-step logger. **LangChain** and **LlamaIndex** are two Python libraries that have already built those pieces. They do not do RAG differently: it is still split, embed, search, assemble a prompt, and call the model. They simply name each stage and give you pre-made building blocks.

Think of it like building a table. With hand tools and raw lumber, you understand every screw, but it takes effort. With a flat-pack kit, assembly is much faster; however, when the manufacturer changes the screw design, old tutorials online no longer match, and you have to figure out which bag the new screw is in.

To decide which approach fits your project, ask yourself three questions:

1. Is your pipeline fixed with only a few steps?
2. Do you need multiple data sources, multiple vector stores, or multiple providers?
3. Are you willing to update your code whenever the library changes its API?

If your answers are "yes, no, no", writing it yourself makes sense. The further your answers drift from that, the more a framework is worth considering.

**The problem: rewrite a minimal RAG pipeline in LangChain and in LlamaIndex, understand which concept in each library maps to each stage, and know the trade-offs of adopting them.**

## Theory

This lesson introduces no new math formulas. The theory here is how the two libraries slice a RAG pipeline into abstractions, and how each library wires those abstractions together.

### Five stages, two sets of names

A RAG pipeline has five stages. The two libraries give different names to the exact same jobs:

1. **Loading documents.** A document loader reads files or web pages and returns `Document` objects, each containing text and **metadata** (such as the source filename). LangChain keeps most loaders in the `langchain-community` package. LlamaIndex calls them readers—for example, `SimpleDirectoryReader` reads an entire folder.
2. **Splitting into chunks.** A text splitter divides each `Document` into chunks while preserving metadata for every chunk. LangChain provides `RecursiveCharacterTextSplitter`, which tries splitting on double newlines first, then single newlines, then spaces, keeping each chunk under `chunk_size` **characters**. LlamaIndex calls this stage a node parser and calls each chunk a **node**; `SentenceSplitter` tries to keep whole sentences intact and measures `chunk_size` in **tokens**.
3. **Embedding and storing.** Compute a vector for each chunk and save it in a vector store. In LangChain, that is `OpenAIEmbeddings` paired with a store like `InMemoryVectorStore`. In LlamaIndex, `VectorStoreIndex` bundles both: creating an **index** splits, embeds, and stores in a single call.
4. **Retrieval.** A **retriever** is an object that takes a question and returns the most relevant chunks. It hides how the search is performed—whether cosine similarity over a vector store, keyword search, or a hybrid of both, the caller only sees "question in, chunks out."
5. **Prompt assembly and model call.** In LangChain, you explicitly pipe the retriever, prompt, model, and output parser into a **chain**. In LlamaIndex, a **query engine** wraps retrieval, prompt construction, and the model call behind a single `query` method.

### LangChain: assembling blocks with LCEL

Every building block in LangChain (prompt, chat model, retriever, output parser) is a **Runnable**: an object with an `invoke` method that takes an input and returns an output. The `|` operator chains two Runnables into one: the output of the left block becomes the input of the right block, just like a pipe in a shell command. This style is called **LCEL** (LangChain Expression Language). Here is the chain from this lesson's code:

```python
chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt | llm | StrOutputParser()
)
```

Read it from left to right, starting with the question string as input:

- **The leading dict** runs two branches on the same question. In the `context` branch, the retriever returns a list of `Document` objects, and the `format_docs` function joins their text into a single string. LangChain automatically wraps a plain Python function into a Runnable when it appears next to `|`. In the `question` branch, `RunnablePassthrough()` passes the question through untouched. The result is a dict `{"context": ..., "question": ...}`.
- **`prompt`** is a `ChatPromptTemplate` with two placeholders, `{context}` and `{question}`. It fills in the dict values and produces a list of `system` and `human` messages.
- **`llm`** (`ChatOpenAI`) sends those messages to the API and returns a model message.
- **`StrOutputParser()`** extracts the text string from that message.

The advantage of this style is that the pipeline sits out in the open: if you want to insert a step—say, rewriting the question before searching—you slot a block into the exact spot. The downside is that you have to wire it yourself and keep track of the data shape at each stage.

### LlamaIndex: index and query engine

LlamaIndex takes the opposite approach: it bundles more out of the box. You configure global defaults once in **`Settings`** (chat model, embedding model, chunk splitter), and then two lines do the rest:

```python
index = VectorStoreIndex.from_documents([doc])
query_engine = index.as_query_engine(similarity_top_k=2)
```

`from_documents` splits documents into nodes using `Settings.node_parser`, embeds each node using `Settings.embed_model`, and stores them in an in-memory vector store. `as_query_engine` returns a query engine; when you call `query_engine.query(question)`, it finds the `similarity_top_k` closest nodes (2 by default), builds a prompt, calls `Settings.llm`, and returns a `Response` object. Printing `Response` gives the answer text, while `response.source_nodes` reveals which nodes were used. Because the pipeline is hidden, `source_nodes` is the easiest place to check what the model relied on.

Two important details about what happens under the hood:

- **Missing settings default to OpenAI.** If you forget to set `Settings.llm` or `Settings.embed_model`, LlamaIndex falls back to OpenAI's models and OpenAI's endpoint, and **does not read** `OPENAI_BASE_URL`. If a Gemini or Ollama user forgets one line, the program sends their key to OpenAI's servers.
- **The built-in prompt has its own wording.** The system instruction opens with "You are an expert Q&A system…", and the context block starts with "Context information is below." (see the Illustration section). If you want to control the tone, language, or strictness of the rules, pass your own prompt via `text_qa_template`. Because this template replaces **both** the default system instructions and the context wrapper, make sure to include all your rules in it:

```python
from llama_index.core import PromptTemplate

qa_prompt = PromptTemplate(
    "Context:\n{context_str}\n\n"
    "Answer using only the context above.\n"
    "Question: {query_str}"
)
query_engine = index.as_query_engine(text_qa_template=qa_prompt)
```

### Connecting to OpenAI-compatible APIs

Both libraries provide classes for OpenAI-compatible APIs, but their parameter names differ. This is the easiest place to trip up when porting code between the two:

| Task | LangChain | LlamaIndex |
|---|---|---|
| Chat model class | `ChatOpenAI` (package `langchain-openai`) | `OpenAILike` (package `llama-index-llms-openai-like`) |
| API base URL | `base_url=` | `api_base=` |
| Embedding model name | `model=` | `model_name=` |
| Extra flag required | `check_embedding_ctx_length=False` on `OpenAIEmbeddings` | `is_chat_model=True` on `OpenAILike` |

Why those last three flags matter:

- **`model_name=`, not `model=`.** LlamaIndex's `OpenAIEmbedding` validates the `model` parameter against an enum of OpenAI model names. Passing any other name—such as an Ollama embedding model—immediately raises `ValueError: '...' is not a valid OpenAIEmbeddingModelType`. The `model_name` parameter bypasses that check.
- **`check_embedding_ctx_length=False`.** By default, `OpenAIEmbeddings` tokenizes text with `tiktoken` and sends **arrays of token IDs** instead of raw strings. OpenAI's own API accepts token ID arrays, but the `langchain-openai` documentation notes that many other providers do not, and recommends setting `False` to send plain text. Testing against a mock server confirms this: with the default setting the server receives lists of integers, whereas with `False` it receives strings.
- **`is_chat_model=True`.** `OpenAILike` defaults to legacy completion mode: it sends a single prompt string to `/completions` instead of a message list to `/chat/completions`. Many providers only expose the chat endpoint; our mock server does too, returning a 404 error if this flag is omitted.

The embedding setup in both code cells reads the same environment variables as [RAG and Modern Chatbots](/en/llm/rag-chatbot/): `EMBEDDING_MODEL` is required, while `EMBEDDING_BASE_URL` and `EMBEDDING_API_KEY` are optional and fall back to the chat endpoint and key when unset. Therefore, if you use OpenAI for embeddings while using another provider for chat, you must explicitly set `EMBEDDING_BASE_URL` to `https://api.openai.com/v1`; leaving it blank sends embedding requests to your chat provider's URL.

### What has changed (tested 10/2026)

Both libraries evolve rapidly, so most examples you find online were written for older versions. Everything below was tested with `langchain` 1.4.7, `langchain-classic` 1.0.8, and `llama-index-core` 0.14.25 in October 2026; newer releases may differ.

- **LangChain 1.x split and removed many modules.** `from langchain.chains import RetrievalQA` and `from langchain.text_splitter import ...` now raise `ModuleNotFoundError`. Legacy chains such as `RetrievalQA` live in a separate `langchain-classic` package (imported from `langchain_classic.chains`) and are marked deprecated. Text splitters live in `langchain-text-splitters`; `Document`, prompts, and the in-memory vector store live in `langchain-core`.
- **LangChain renamed its agent constructor.** LangGraph's `create_react_agent` moved to `create_agent` in `langchain.agents`. LangChain's official RAG tutorial now builds on Deep Agents (package `deepagents`, function `create_deep_agent`), where an agent decides when to call a search tool. Meanwhile, the Retrieval concept guide still documents "2-Step RAG" (always retrieve first, then call the model)—matching the chain in this lesson—and notes that it fits Q&A bots and documentation assistants well. An LCEL chain like ours still works and is ideal for learning each stage; agents are covered in [Agents](/en/llm/agents/).
- **Install LlamaIndex selectively.** The umbrella package `llama-index` 0.14.25 requires `llama-index-llms-openai` below 0.8, whereas `llama-index-llms-openai-like` 0.8.1 requires 0.8 or higher, causing pip to report a conflict. Installing `llama-index-core` alongside only the specific integration packages you need works cleanly, just as LlamaIndex's installation guide recommends.
- **LlamaIndex does not yet accept `openai` 3.** `llama-index-llms-openai` pins `openai` below 3, whereas the other lessons in this part use `openai` 3.37. `langchain-openai` 1.7.2 accepts both.

### Limitations

- **The vector stores in both code cells live in memory.** Exiting the program wipes them out, so the next run re-embeds everything from scratch and calls the API again. Production apps persist indexes to disk or use a dedicated vector database.
- **A framework does not make RAG more accurate.** Retrieval quality still depends on how you split chunks, which embedding model you pick, $k$, and your prompt. The evaluation practices from [RAG and Modern Chatbots](/en/llm/rag-chatbot/) remain just as necessary.
- **This lesson only touches the RAG slice.** Both libraries also support agents (LangChain builds agents on LangGraph; LlamaIndex has `FunctionAgent`), which are the topic of [Agents](/en/llm/agents/).

| Wiring steps together | a few lines of Python | LCEL chain: `\|` | `query_engine.query(...)` |

## Common pitfalls

:::caution[Copying code from old tutorials, or installing both libraries in one environment]
Examples online often start with `from langchain.chains import RetrievalQA` or `from langchain.text_splitter import ...`. In `langchain` 1.x, both raise `ModuleNotFoundError`. Do not blindly install extra packages until the error goes away: check which version the tutorial used, read the docs for the version you installed, and pin versions in `requirements.txt`. Similarly, installing the umbrella `llama-index` package alongside a recent `llama-index-llms-openai-like` triggers a pip conflict, and installing LlamaIndex into an environment with `openai` 3 silently downgrades `openai`. Give each project its own virtual environment.
:::

:::caution[Mixing up parameter names, or forgetting LlamaIndex's `Settings`]
`base_url` is LangChain's name; LlamaIndex calls it `api_base`. LlamaIndex's embedding class takes a custom model name via `model_name`; writing `model=` with a non-OpenAI model name raises a `ValueError`. Forgetting `is_chat_model=True` makes `OpenAILike` call the legacy `/completions` endpoint, causing chat-only providers to return a 404 error. Worst of all is forgetting `Settings.llm` or `Settings.embed_model`: LlamaIndex silently defaults to OpenAI, sends your other provider's key to OpenAI's servers, and gets an `AuthenticationError` (401). If you see a 401 error when you are not even using OpenAI, check `Settings` first.
:::

:::caution[Assuming a framework makes RAG more accurate or cheaper]
A framework only packages the steps; poorly split chunks, a weak embedding model, or a vague prompt will still produce poor answers, just as in handwritten code. Nor does a framework reduce API calls: both code cells re-embed the entire document on every run because their vector stores live in memory. With a large corpus, every test run bills you for embeddings again, so persist your index to disk. And as in every API lesson: keep keys in environment variables, never in code, even when a framework lets you pass `api_key="..."` directly.
:::

## Summary and further reading

**Key takeaways:**

- LangChain and LlamaIndex do not change how RAG works: it is still load documents, split chunks, embed and store, retrieve, assemble a prompt, and call the model. They name and pre-build each stage. When your pipeline is fixed, short, and uses a single provider, handwritten code is usually enough.
- LangChain pipes Runnable blocks together with LCEL: `{"context": retriever | format_docs, "question": RunnablePassthrough()} | prompt | llm | StrOutputParser()`. The pipeline is explicit and easy to insert steps into.
- LlamaIndex bundles the pipeline: configure `Settings` once, build an index with `VectorStoreIndex.from_documents`, and answer questions with `as_query_engine`; `response.source_nodes` shows which chunks were used. You can replace the default prompt via `text_qa_template`.
- Both libraries change rapidly: parameter names differ (`base_url` vs. `api_base`, `model` vs. `model_name`), missing LlamaIndex settings silently fall back to OpenAI, and legacy LangChain imports have been removed. Pin package versions and use separate virtual environments.
