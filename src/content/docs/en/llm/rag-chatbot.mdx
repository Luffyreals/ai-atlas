:::tip[Quick refresher]
**Information retrieval** is the task of ranking a collection of documents by relevance to a given query. Classical methods match **keywords**: **TF-IDF** (term frequency–inverse document frequency) assigns each word a weight that grows when the word appears often in a document but rarely across the collection; **BM25** is a refined scoring function in the same family. A second approach uses **embeddings**: a model maps each passage to a vector of numbers so that passages with similar meaning land close together. To measure how close two vectors point, we use **cosine similarity**—the cosine of the angle between them, which the Theory section derives step by step. We also reuse the XML-tag delimiter technique from [Prompt Engineering](/en/llm/prompt-engineering/) to separate instructions from data.
:::

## Intuition

Suppose your company has an 80-page employee handbook covering annual leave, remote work, payroll, health insurance, and office equipment. Every day the HR team answers the same recurring questions. You want to build a chatbot to answer them automatically.

Asking a general chat model directly will not work. It has never read your company's internal handbook, so it will answer based on "what companies typically do"—sounding completely confident while potentially being completely wrong. When a model confidently fabricates facts like that, it is called **hallucination**.

A second idea is to paste all 80 pages into the prompt on every single question. That burns huge numbers of input tokens on **every** call, can exceed the context window as the document library grows, and forces the model to hunt for a needle inside a very long context.

A third approach works like an **open-book exam**. A student taking an open-book exam does not memorize all 80 pages ahead of time; when given a question, they flip to the relevant page, read two or three paragraphs, and write their answer from those paragraphs. RAG works the exact same way: **retrieve a few relevant passages from your document store, paste them into the prompt, and instruct the model to answer strictly from those passages.** None of the model's weights change, and whenever the handbook is updated, you simply update the document store.

Of course, if the student flips to the wrong page, even the brightest student will give the wrong answer. Everything hinges on the retrieval step. Suppose the handbook says: *"Each week, employees may work remotely for up to two days."* If someone asks *"Can I work remotely?"*, keyword search easily finds the passage because the question shares the exact words `"work"` and `"remotely"`. If someone asks *"Can I do my job from home?"*, the meaning is identical, yet the question shares none of the content words. Our first code example will show keyword search failing on that exact question.

The problem this lesson solves is: **given a document collection and a user question, retrieve the passages that match by meaning rather than just exact wording, and have the model answer strictly from those passages with verifiable source citations.**

## Theory

### Two stages of RAG

The term comes from [Lewis et al. (2020)](https://arxiv.org/abs/2005.11401), who combined a language model's weights—its **parametric memory**—with an external document index—its **non-parametric memory**. (In their paper, the query encoder and generator were fine-tuned jointly while keeping the document encoder and index fixed; in the API-based RAG pattern used here, **nothing is trained**—we retrieve passages and assemble a prompt.)

Every RAG system operates in two distinct stages:

1. **Indexing**, run once ahead of time (and rerun whenever documents change): split documents into smaller passages, convert each passage into an embedding vector, and store the vectors alongside the text.
2. **Querying**, run on every user question: convert the question into an embedding vector, find the $k$ passages whose vectors are closest, paste those passages into a prompt, and call the chat model.

### Indexing: chunks, embeddings, and the vector store

**Step 1: chunking.** Split each document into smaller **document chunks** (or passages). (Do not confuse these with streaming chunks in [Using Text Generation APIs](/en/llm/text-api/)—same English word, different concept.) Why not compute a single embedding vector for the entire 80-page handbook? Because one vector averaging hundreds of paragraphs blurs every topic together and matches no specific question well—and pasting all 80 pages into the prompt brings back the token-cost problem. Choosing chunk size is a trade-off:

- **Chunks that are too long** mix several topics together, diluting similarity scores and spending more prompt tokens per retrieved chunk.
- **Chunks that are too short** lose crucial context: a standalone sentence like *"This rate applies starting from the second year"* is useless if the previous sentence explaining what *"this rate"* refers to was cut into a different chunk.

Common chunking strategies split by a fixed character or token count, or along natural boundaries such as paragraphs and section headings, while keeping a small **overlap** between consecutive chunks so ideas sitting near a boundary are not sliced in half. There is no universal "best" chunk size or overlap: both are **hyperparameters** that you tune on your own documents and evaluation questions. A chunk must also stay within the embedding model's maximum input length (for example, OpenAI lists an 8,192-token input limit for its current embedding models as of October 2026).

Every chunk should carry its **source metadata** alongside its text: document title, section heading, or `url`. In [Web Crawling and MongoDB](/en/llm/web-crawling-mongodb/), we store `url` and `fetched_at` with each crawled page for this exact purpose: the chatbot needs them to cite its sources.

**Step 2: embeddings.** Send the chunks to an embedding model to obtain one numerical vector per chunk. With the `openai` SDK, you call `client.embeddings.create(model=..., input=[...])`, where `input` accepts either a single string or a batch list of strings, and the $i$-th vector is returned at `response.data[i].embedding`. Remember that an embedding model is a **separate model** from your chat model: it does not generate prose, it only outputs vectors. Real embedding vectors have hundreds or thousands of dimensions; individual coordinates have no human-readable label, and only the geometric closeness between vectors carries meaning.

**Step 3: the vector store.** A vector store holds the embedding vector, raw text, and source metadata of every chunk, and answers nearest-neighbor queries. For a few thousand chunks, an in-memory NumPy matrix is plenty: comparing a question vector against **every** chunk vector is a single matrix–vector multiplication, as shown in our second code example. When a collection grows to millions of chunks, scanning every vector becomes too slow, so dedicated libraries like [FAISS](https://github.com/facebookresearch/faiss) or [Chroma](https://github.com/chroma-core/chroma) build **approximate nearest neighbor (ANN)** indexes that trade a tiny fraction of recall for much faster search.

### Cosine similarity

Given two vectors $\mathbf{a}, \mathbf{b} \in \mathbb{R}^n$, where $n$ is the embedding dimension, their **cosine similarity** is:

$$
\cos(\mathbf{a}, \mathbf{b}) = \frac{\mathbf{a} \cdot \mathbf{b}}{\lVert \mathbf{a} \rVert \, \lVert \mathbf{b} \rVert}
$$

Let's read each piece of the formula:

- **The numerator** is the dot product $\mathbf{a} \cdot \mathbf{b} = \sum_{j=1}^{n} a_j b_j$: multiply matching coordinates and add them up. When two vectors have large values with the same sign in the same dimensions, their dot product is large.
- **The denominator** is the product of the two Euclidean lengths (norms), where $\lVert \mathbf{a} \rVert = \sqrt{\sum_{j=1}^{n} a_j^2}$.
- **Why it is called cosine.** In Euclidean geometry, $\mathbf{a} \cdot \mathbf{b} = \lVert \mathbf{a} \rVert \, \lVert \mathbf{b} \rVert \cos\varphi$, where $\varphi$ is the angle between the two vectors. Dividing by the product of the lengths isolates $\cos\varphi$, which always lies in $[-1, 1]$: it equals $1$ when the vectors point in the exact same direction, $0$ when they are perpendicular, and $-1$ when they point in opposite directions.

**Cosine similarity is invariant to vector length.** Multiply $\mathbf{a}$ by any positive scalar $t > 0$:

$$
\cos(t\mathbf{a}, \mathbf{b}) = \frac{t \, (\mathbf{a} \cdot \mathbf{b})}{t \, \lVert \mathbf{a} \rVert \, \lVert \mathbf{b} \rVert} = \cos(\mathbf{a}, \mathbf{b})
$$

Scaling every coordinate of $\mathbf{a}$ by $t$ multiplies the dot product in the numerator by $t$ and also multiplies the length $\lVert \mathbf{a} \rVert$ in the denominator by $t$, so the two factors of $t$ cancel out. Picture each vector as an arrow from the origin: two passages on the exact same topic—one short, one long—may produce arrows of different lengths that point in the same direction. Because cosine similarity only looks at direction, length differences do not skew the ranking.

**Worked numerical example.** Take 3-dimensional toy vectors with query $\mathbf{q} = (1, 2, 0)$ and three candidate chunks. First note that $\lVert \mathbf{q} \rVert = \sqrt{1 + 4 + 0} = \sqrt{5}$.

| Chunk | Vector | Dot product with $\mathbf{q}$ | Length | Cosine similarity |
|---|---|---:|---:|---:|
| $\mathbf{c}^{(1)}$ | $(2, 4, 0)$ | $2 + 8 + 0 = 10$ | $\sqrt{20} = 2\sqrt{5}$ | $10 / (\sqrt{5} \cdot 2\sqrt{5}) = 1$ |
| $\mathbf{c}^{(2)}$ | $(6, 3, 0)$ | $6 + 6 + 0 = 12$ | $\sqrt{45} = 3\sqrt{5}$ | $12 / (\sqrt{5} \cdot 3\sqrt{5}) = 0.8$ |
| $\mathbf{c}^{(3)}$ | $(0, 1, 2)$ | $0 + 2 + 0 = 2$ | $\sqrt{5}$ | $2 / (\sqrt{5} \cdot \sqrt{5}) = 0.4$ |

Notice that $\mathbf{c}^{(1)} = 2\mathbf{q}$ points in the exact same direction as the query, giving a cosine similarity of $1$. Yet if you ranked by raw dot product without dividing by length, $\mathbf{c}^{(2)}$ would win ($12 > 10$) simply because its coordinates are larger. That is why we divide by the vector norms.

**Pre-normalizing for speed.** If both vectors already have unit length $1$, the denominator is $1 \cdot 1 = 1$, and cosine similarity reduces to the plain dot product. In practice, systems **normalize** each vector to unit length once during indexing via $\mathbf{u} = \mathbf{a} / \lVert \mathbf{a} \rVert$. At query time, scoring all chunks is then a single fast matrix–vector multiplication. (OpenAI documents that its embedding vectors are already normalized to length 1; with other providers, never assume—normalize explicitly as we do in our second code example.)

:::note[Key takeaway]
Cosine similarity $\cos(\mathbf{a}, \mathbf{b}) = \dfrac{\mathbf{a} \cdot \mathbf{b}}{\lVert \mathbf{a} \rVert \, \lVert \mathbf{b} \rVert}$ compares only the direction of two vectors and lies in $[-1, 1]$. Once all vectors are normalized to unit length 1, cosine similarity equals the dot product.
:::

### Querying: top-k, context-augmented prompt, and citations

**Top-$k$ retrieval.** Suppose your index holds $m$ chunks with embedding vectors $\mathbf{c}^{(1)}, \dots, \mathbf{c}^{(m)}$. Embed the user's question with the **exact same embedding model** used during indexing to get $\mathbf{q}$, and score every chunk:

$$
s^{(i)} = \cos\left(\mathbf{q}, \mathbf{c}^{(i)}\right), \quad i = 1, \dots, m
$$

Sort the scores $s^{(i)}$ in descending order and keep the top $k$ chunks. In the 3-chunk toy table above, $k = 2$ keeps $\mathbf{c}^{(1)}$ and $\mathbf{c}^{(2)}$. (Do not confuse this with top-k token sampling in [Using Text Generation APIs](/en/llm/text-api/): both simply mean "keep the top $k$ highest-scoring items".)

The number of retrieved chunks $k$ is another hyperparameter. If $k$ is too small, you risk leaving out the chunk that holds the answer. If $k$ is too large, you pay for extra tokens on every call, pull in irrelevant distractor chunks, and bury the relevant chunk in the middle of a long context—where, as [Liu et al. (2023)](https://arxiv.org/abs/2307.03172) showed, language models often struggle to attend to it reliably. (Their study tested multi-document question answering and synthetic key–value retrieval, so treat it as a practical caution rather than a rigid law.)

**Assembling the prompt.** The prompt sent to the chat model combines three pieces, building directly on [Prompt Engineering](/en/llm/prompt-engineering/):

- **System instructions:** answer strictly from the provided passages; if the passages do not contain the answer, state clearly that the documents do not cover it; cite the number of each passage used.
- **The retrieved chunks, numbered** `[1]`, `[2]`, … and enclosed inside delimiter tags such as `<docs>`. Delimiters separate data from instructions—which is critical because retrieved chunks come from external documents (sometimes crawled from the web) and could contain indirect prompt injection payloads.
- **The user's question.**

**Citations.** Instruct the model to write markers like `[1]` after each claim, and let **your application code** map `[1]` back to the actual document title or URL—because your code knows exactly which chunk it placed in slot `[1]`. Never ask the LLM to type out URLs or file paths from memory. Even with numbered brackets, a model might still hallucinate a citation number that does not exist (such as `[3]` when you only passed $k = 2$ chunks) or cite `[2]` for a claim that chunk 2 never made. The first failure can be caught deterministically in code, as shown in our second code example; catching the second requires showing the source passage to the user (or checking it in an evaluation pass).

**Keyword search vs. embeddings.** Keyword retrieval (TF-IDF, BM25) only matches when the question and chunk **share exact words**, whereas embedding-based retrieval (**dense retrieval**) matches by semantic meaning. [Karpukhin et al. (2020)](https://arxiv.org/abs/2004.04906) showed that their dense retriever outperformed BM25 by roughly 9 to 19 percentage points in top-20 passage retrieval accuracy across several English QA benchmarks. That does not make keyword search obsolete: TF-IDF and BM25 are fast, require no API calls, and excel at matching exact strings that embeddings often blur—such as product serial numbers, error codes, or proper names. Many production systems run **hybrid search**, combining keyword and dense retrieval scores.

### Evaluating RAG with synthetic data

When you change chunk size, change $k$, or swap embedding models, how do you know whether retrieval improved? Just as in [Prompt Engineering](/en/llm/prompt-engineering/), you need an **evaluation set (eval)**. For the retrieval step, each test case pairs a question with the ground-truth chunk that answers it. Writing hundreds of pairs by hand is tedious, so teams often bootstrap an eval set using **synthetic data**:

1. Loop over your chunks and ask an LLM to write one or two questions that each chunk can answer. This immediately gives you `(question, source_chunk)` pairs.
2. Run your retrieval step on every generated question.
3. Measure **hit rate** at $k$: the fraction of questions for which the ground-truth `source_chunk` appears among the top-$k$ retrieved chunks. A hit rate of $0.8$ at $k = 3$ means 80% of questions retrieve their target chunk within the top 3 results.

One important caveat: when an LLM writes a question while looking directly at a chunk, it tends to **reuse the exact phrasing of that chunk**. Retrieval on synthetic questions is therefore noticeably easier than on real user questions phrased in everyday language (like *"do my job from home"* vs. *"work remotely"*), making synthetic hit rate overly optimistic. Always review generated questions to filter out nonsensical ones, and mix in real user queries as soon as you have them.

Remember that hit rate only scores the retrieval step. The final answer can still go wrong even when the right chunk is retrieved—for instance, if the chat model misreads the passage or embellishes it with outside assumptions. Frameworks like Ragas ([Es et al., 2024](https://aclanthology.org/2024.eacl-demo.16)) use LLM judges to score faithfulness and answer relevance separately. Evaluating open-ended text generation in general is covered in [Model Evaluation and PEFT](/en/llm/evaluation-peft/).

### From RAG to a full chatbot

A real-world chatbot rarely sends every single user message straight through RAG. Three architectural building blocks often sit around the RAG pipeline:

**Semantic router.** If a user types *"Hello!"*, there is no point searching the employee handbook; if they ask for today's gold price, the chatbot should politely decline. A semantic router picks a handling path for each incoming message **by meaning**, acting like a receptionist who listens to your question and directs you to the right desk. Each route is defined by a handful of example utterances:

| Route | Example utterances | Action taken |
|---|---|---|
| Handbook QA | `"How many days of annual leave do I get?"`, `"When is payday?"` | Run the RAG pipeline |
| Greeting / chitchat | `"Hello"`, `"Thanks a lot"` | Reply briefly without retrieval |
| No route matched | (highest cosine similarity falls below threshold) | Explain that the chatbot only covers the employee handbook |

When a new message arrives, the router embeds it, computes cosine similarity against all pre-embedded route examples, and picks the route of the closest example **if** its similarity exceeds a threshold; otherwise it falls back to "no route matched". The open-source [semantic-router](https://github.com/aurelio-labs/semantic-router) library by Aurelio Labs implements this pattern (in v0.x via `score_threshold`, and in v1.x via threshold calibration on labeled queries). Routing via embeddings is faster and cheaper than asking a chat LLM to classify every message, since it requires only a single embedding call. The trade-off is that cosine similarity scales vary across embedding models—the same pair of sentences might score $0.4$ under one model and $0.7$ under another—so you must tune the threshold empirically on sample queries whenever you pick or change an embedding model.

**Reflection (self-check).** Once the chat model drafts an answer, you can make an extra LLM call to review the draft before showing it to the user—like proofreading an essay before handing it in: does every claim in the draft appear in the retrieved chunks, are citations attached, and does the draft actually answer the question? If the check fails, the system can revise the answer or rewrite the query and retrieve again. This pattern draws inspiration from Self-Refine ([Madaan et al., 2023](https://arxiv.org/abs/2303.17651)), where a model critiques and refines its own output, and Reflexion ([Shinn et al., 2023](https://arxiv.org/abs/2303.11366)), where an agent records verbal feedback across trials—neither updates model weights, and neither was designed specifically for RAG. Because every reflection pass adds an extra LLM call (increasing both latency and token cost), cap the loop at one or two iterations at most.

**Follow-up questions in multi-turn chat.** Suppose a user asks *"How many days of annual leave do I get?"* and then follows up with *"What about unused ones?"* Embedding the second question on its own fails because *"unused ones"* lacks the subject *"annual leave days"*. The standard fix is a **query rewriting** step: pass the conversation history and the follow-up question to the LLM, ask it to rewrite the follow-up into a standalone question (*"What happens to unused annual leave days?"*), and embed that rewritten question for retrieval.

### Limitations

- **Questions that require aggregating across many documents**—such as *"which department has the most remote-work requests?"*—cannot be answered by fetching a few isolated chunks. [Graph RAG](/en/llm/graph-rag/) explores representing knowledge as a graph for multi-hop and global questions.
- **Access control.** If you dump confidential executive memos and public handbook pages into the same vector store without metadata filtering, the chatbot can leak restricted chunks to unauthorized users. Always filter candidate chunks by the querying user's permissions *before* inserting them into the prompt.
- **The code in this lesson is intentionally minimal** so every line is transparent. Frameworks covered in [LangChain and LlamaIndex](/en/llm/langchain-llamaindex/) provide higher-level abstractions for document loaders, chunkers, and vector stores.

### A minimal RAG pipeline

This script puts the entire Theory section into action: it embeds the 5 chunks once (indexing), normalizes every vector to unit length, scores all chunks against each question with a single matrix–vector product `index @ ...`, takes the top-2 chunks, formats the `<docs>` prompt shown in the Illustration section, calls the chat model, and finally checks in code whether the model cited any non-existent chunk numbers.

In addition to the three environment variables from [Using Text Generation APIs](/en/llm/text-api/#setup-providers-and-environment-variables), this script reads `EMBEDDING_MODEL`: the name of an embedding model (which is distinct from the chat model in `LLM_MODEL`). By default, the script sends embedding calls to the **same** `base_url` and API key as chat calls. If your chat provider does not offer an embeddings endpoint (check the provider table in the first lesson), set `EMBEDDING_BASE_URL` and `EMBEDDING_API_KEY` to point at a provider that does—such as Gemini, or a local Ollama server (set the key to `ollama` and run `ollama pull` for an embedding model first). If your fallback embedding provider is OpenAI itself while your chat provider is something else, set `EMBEDDING_BASE_URL="https://api.openai.com/v1"` explicitly, because leaving it empty tells the script to reuse the chat provider's `base_url`.

## Common pitfalls

:::caution[Assuming RAG completely eliminates hallucination]
RAG reduces hallucination, but does not make it impossible. If retrieval fetches the wrong chunks, the model may still answer confidently from the wrong passage; even when retrieval fetches the right chunk, the model may blend in outside assumptions. A high cosine score does not guarantee an answer is present either—it only measures closeness in embedding space. State clearly in the system prompt *"answer only from the provided chunks; if they hold no answer, say so"*, measure retrieval hit rate, and show source passages to the user so they can verify critical claims.
:::

:::caution[Embedding queries and chunks with two different models]
Every embedding model defines its own coordinate space, so taking the cosine similarity between a query vector from model A and a chunk vector from model B is meaningless—even if both vectors happen to have the same number of dimensions. Always embed queries with the exact model used during indexing, and re-index your entire store whenever you switch embedding models. Two related configuration mistakes: putting a chat model name into `EMBEDDING_MODEL` (which usually raises an API error, or returns vectors unsuitable for retrieval), and calling `embeddings.create` against a provider that does not serve embeddings. Both errors will surface immediately on the `index = embed(...)` line before the first question runs.
:::

:::caution[Assuming a larger $k$ is always safer, or trusting model-written citations blindly]
Increasing $k$ increases token cost on every query and stuffs more irrelevant chunks into the prompt. Tune $k$ on an evaluation set rather than guessing. Likewise, remember that `[1]` in the model's reply is still generated text: verify in code that cited numbers actually exist in `1..k`, and let your program—not the LLM—print the source title or URL.
:::

## Summary and further reading

**Key takeaways:**

- RAG turns question answering into an open-book exam: index once (chunk documents, compute embeddings, store vectors), then on each query retrieve the top-$k$ closest chunks and place them into the prompt. Model weights never change, and updating knowledge only requires updating the index.
- Cosine similarity $\cos(\mathbf{a}, \mathbf{b}) = \dfrac{\mathbf{a} \cdot \mathbf{b}}{\lVert \mathbf{a} \rVert \, \lVert \mathbf{b} \rVert}$ compares vector direction independently of length. After normalizing vectors to length 1, cosine similarity equals the dot product, and scoring the whole index is a single matrix multiplication. Queries and chunks must use the exact same embedding model.
- Keyword search (TF-IDF, BM25) matches exact words, whereas embeddings match semantic meaning. A RAG prompt combines system instructions, numbered chunks inside delimiter tags, and the user question; application code maps citation numbers to sources and checks for invented numbers.
- Chunk size and $k$ are hyperparameters tuned on an evaluation set, such as hit rate on synthetic questions (keeping in mind that synthetic questions are optimistic). Around RAG, a semantic router directs queries using embedding similarity and a threshold, while reflection adds a self-check call at the cost of extra latency and tokens.

- Karpukhin, V., Oğuz, B., Min, S. et al. (2020). [*Dense Passage Retrieval for Open-Domain Question Answering*](https://arxiv.org/abs/2004.04906). EMNLP 2020. Demonstrates why dense embedding retrieval outperforms BM25 on semantic paraphrases and how dual encoders are trained.
