## Goals

After this lesson, you will be able to:

- Send an image to a vision-capable model by placing the image inside `messages` as a base64 **data URL** alongside your text question.
- Generate an image from a text prompt using `images.generate`, decode the `b64_json` response, and save it to a file.
- Explain why video generation is an **asynchronous job**: submit a request, keep the job `id`, check status via **polling**, and download the output before the temporary link expires.
- Recognize the practical boundaries around AI-generated media: **content moderation**, copyright, and why provenance markers like C2PA do not prove by themselves whether an image is real or fake.

## Intuition

You already know how to send text to a model and get text back. Now three new requests land on your desk:

1. Snap a photo of a receipt and ask the model, "What is the total amount?".
2. Ask a model to paint a watercolor illustration for a blog post.
3. Ask a model to render an eight-second video clip.

On the surface they sound identical: send a request, get a result. At the API layer, however, they follow three completely different paths.

**Asking about an image** is still a chat conversation. You still call `chat.completions`, except your user message now contains two parts: a text question and an image. The model replies in text, just like before.

**Generating an image** goes through a separate door: `images.generate`. In goes a prompt; out come the bytes of a new image. There is no `messages` list and no multi-turn history. Many beginners assume a single endpoint handles both, and are puzzled when a chat model replies with a vivid text description instead of a picture.

**Generating a video** takes minutes. Nobody holds an HTTP request open that long. Instead, it works like shipping a package: you place an order, receive a **tracking number**, and check back periodically to see where it is. Once the package arrives at the pickup locker, you have to collect it promptly because the locker only holds it for a short window.

**The problem: using the familiar `openai` SDK, send an image for a vision model to read, generate a brand-new image from a prompt, and understand the asynchronous job pattern used for long-running tasks like video—along with the safety and provenance realities of AI-generated media.**

## Theory

### Putting images inside `messages`

In the previous lesson, the `content` of a message turn was a string. To send an image, the `content` of the `user` turn becomes a **list of content parts**, each tagged with a `type`:

```json
{
  "role": "user",
  "content": [
    { "type": "text", "text": "What shapes and colors are in the image, and where?" },
    { "type": "image_url", "image_url": { "url": "data:image/png;base64,iVBORw0KGgo..." } }
  ]
}
```

A single user turn can interleave multiple text parts and multiple images. The model reads them in order and replies with **text**: the `assistant` turn still has a plain string `content`, just as in text-only chat.

**The `url` field accepts two kinds of values.** Even though the field is named `image_url`, its `url` does not have to be an HTTP link:

- **A web URL** (`https://...`): the provider's servers fetch the image over the internet. The URL must be publicly accessible.
- **A data URL**: a self-contained string that carries the image bytes inline, formatted as `data:<MIME type>;base64,<data>`. For example, `data:image/png;base64,iVBORw0KGgo...`. The MIME type (`image/png`, `image/jpeg`, and so on) must match the actual file format.

Across the documentation for OpenAI, Gemini, Groq, and Ollama (checked 10/2026), all four accept base64 data URLs, whereas Ollama **does not** accept web URLs in `image_url`. For that reason, this lesson's code uses data URLs—the most portable format across providers.

**Base64 inflates size by roughly one third.** Base64 encodes binary bytes using 64 text-safe ASCII characters (`A`–`Z`, `a`–`z`, `0`–`9`, `+`, `/`). Each character carries 6 bits. Three bytes equal 24 bits, which fit neatly into four Base64 characters. If the final group has fewer than three bytes, `=` padding characters are appended to complete the four-character block. Thus a file of $s$ bytes becomes a string of length:

$$
4\left\lceil \frac{s}{3} \right\rceil
$$

characters, where $\lceil\cdot\rceil$ rounds up to the nearest integer. For large $s$, the ratio is $4/3 \approx 1.33$: a 3 MB photo turns into a ~4 MB string inside your JSON request body. Resize large images before sending them. Every provider also enforces its own limits on image dimensions, file size, and number of images per request—check your provider's docs for the exact numbers.

**Images cost tokens too.** The model does not read the raw base64 characters as text. Instead, the provider decodes the image and converts it into a sequence of visual tokens fed into the model. Larger, higher-resolution images consume more tokens and cost more. OpenAI also supports an optional `detail` field inside `image_url` (`"low"`, `"high"`, `"auto"`, etc., depending on the model): `"low"` uses fewer tokens and is plenty when you only need the overall gist of an image. How a language model actually "sees" visual tokens is covered in [Multimodal Models](/en/llm/multimodal/).

**The model must support vision.** Not every chat model accepts images. Sending an image to a text-only model will return a 400 error—or worse, a confident hallucination. Make sure `LLM_MODEL` points to a vision-capable model on your chosen provider.

### Generating images with `images.generate`

Image generation uses a dedicated endpoint, separate from chat:

```python
response = client.images.generate(
    model=IMAGE_MODEL,
    prompt=prompt,
    size="1024x1024",
    n=1,
)
```

- `model`: the image generation model. Because this is distinct from your chat model, our code reads it from a separate environment variable `IMAGE_MODEL`, following the `<CAPABILITY>_MODEL` naming convention used throughout this part.
- `prompt`: a description of the image you want. Crafting effective prompts is covered in [Prompt Engineering](/en/llm/prompt-engineering/).
- `size`: pixel dimensions such as `"1024x1024"`. `n`: how many images to generate.

The results sit in `response.data`, where each item represents one generated image. Most commonly, the image is returned in `b64_json`—a base64 string that you decode with `base64.b64decode` to get the raw image file bytes. Some providers or models return a temporary `url` instead, which expires after a short window and must be downloaded right away. The safest code **checks both fields**, since whichever field is unused will be `None`.

**Not every provider offers image generation.** According to provider documentation checked in 10/2026:

- **OpenAI** supports `images.generate` with provider-specific parameters like `quality`, `output_format`, and `background`. Its GPT Image models return base64-encoded image data.
- **Gemini** (via its OpenAI compatibility layer) supports `images.generate`, but only honors `prompt`, `model`, `n`, `size`, and `response_format`. Any other parameter is **silently ignored** without raising an error. Gemini-specific options such as aspect ratio must be passed through `extra_body`.
- **Groq** and **Ollama**: neither provider's OpenAI compatibility layer exposes an image generation endpoint (as of 10/2026), so the image generation cell cannot be run through them. (Ollama does have experimental CLI image generation outside its OpenAI compatibility layer; see [Ollama's blog post](https://ollama.com/blog/image-generation).)

See the provider table and `OPENAI_BASE_URL` values in [Using Text APIs](/en/llm/text-api/). In practice, you may end up using one provider for vision chat and another for image generation.

### Video: an asynchronous job

Rendering a video clip takes minutes, so a video API never returns the finished video inside the initial HTTP response. Instead, it follows the **asynchronous job** pattern: submit now, collect later.

1. **Create a job.** You send your prompt. The API immediately returns a job `id` and an initial status, typically `queued`.
2. **Wait.** The job transitions through `in_progress` to either `completed` or `failed`. Your code learns about state changes in one of two ways:
   - **Polling**: periodically querying the job status endpoint.
   - **Webhook**: registering an HTTPS callback URL on your server that the provider calls automatically as soon as the job finishes. Webhooks avoid repeated polling calls, but require a publicly reachable server.
3. **Download the output.** Once the job reaches `completed`, fetch the video file and copy it into your own storage bucket immediately, because provider download URLs are short-lived.

In provider-neutral pseudocode, a polite polling loop looks like this:

```text
job = create_job(prompt)           # returns immediately: job.id, job.status = "queued"
wait = 10 seconds
while job.status is not "completed" or "failed":
    if elapsed time > max_timeout: report timeout and stop
    sleep(wait)
    job = get_job_status(job.id)
    wait = min(wait * 2, 60 seconds)   # backoff: poll less frequently over time
if job.status == "failed": report error and stop
download(job.id) and save to your own storage immediately
```

Three habits matter here. Increase the delay between checks (**backoff**), just like retry backoff in the previous lesson, because hammering the status endpoint wastes requests and invites 429 rate limits. Always enforce a **maximum timeout** so your worker does not hang forever on a stuck job. And **save the file to your own storage right away**—for example, OpenAI's former video API documentation recommended polling every 10–20 seconds with backoff (or using webhooks) and noted that download URLs expired after at most one hour.

:::caution[Why this lesson does not include a runnable video code cell]
Video APIs are in rapid flux. As of October 2026: OpenAI shut down its Videos API on September 24, 2026 without a drop-in replacement; Google deprecated its Veo 3.1 preview models on October 22, 2026, and Gemini's newer video generation endpoints use Google's native SDK rather than an OpenAI-compatible `/v1/videos` route. Consequently, there is no stable video snippet that runs through the `openai` SDK to include here. The architectural pattern—create a job, store the `id`, poll with backoff (or use a webhook), and copy the result to your own storage—remains universal. When integrating a specific video provider, consult its current docs and isolate the provider-specific calls behind a thin wrapper.
:::

### Moderation, copyright, and content provenance

**Content moderation.** Providers filter both input prompts and generated images. On OpenAI, a rejected request raises a 400 error with code `moderation_blocked`, and the docs advise against retrying without modifying the prompt: sending the exact same prompt again will simply fail again. Because the SDK does not auto-retry 400 errors, our code catches `openai.BadRequestError` and prints the error code. Note that OpenAI may also require organization verification before granting access to GPT Image models.

**Copyright and likeness rights.** Who owns AI-generated images, and how they may be used commercially, depends on each provider's terms of service and local law. This lesson is not legal advice, but three practical habits will keep you out of obvious trouble:

- Read your provider's terms of service before using generated assets commercially, and consult legal counsel when needed.
- Never feed copyrighted artwork, real people's faces without consent, or protected trademarks into prompts or image inputs.
- Clearly disclose when published images or videos are AI-generated.

**Content provenance** answers the question "Where did this image come from?". Two complementary mechanisms are widely used today:

- **C2PA** (Coalition for Content Provenance and Authenticity) is an open standard known as **Content Credentials**: it attaches a cryptographically signed manifest to a file's metadata recording which camera or AI tool created and edited it. Because the manifest lives in file metadata, it is easily stripped when an image is screenshotted, re-encoded, or uploaded to social media platforms.
- **Invisible watermarks** embed a signal directly into the pixel values. They survive format conversions better than metadata, though heavy cropping or editing can still degrade them. Google, for instance, notes that all images generated by Gemini carry an invisible **SynthID** watermark.

Two conclusions follow: **the absence of a provenance marker never proves an image is human-made**, and **the presence of a marker only tells you which tool produced the file**, not whether the scene it depicts is true.

### Limitations

- **Parameters and formats vary across providers.** The portable core is `messages` with base64 data URLs for vision, and `images.generate` with basic parameters (`model`, `prompt`, `size`, `n`). Everything else requires checking your provider's docs (see the third pitfall below).
- **Vision models still make mistakes**: misreading digits on a blurry receipt or miscounting objects in a crowded scene. Always verify outputs on high-stakes tasks.

## Common pitfalls

:::caution[Assuming `image_url` only accepts web links]
Despite the name, `url` accepts base64 data URLs, and data URLs are the most portable choice across providers (Ollama only accepts base64). Two small bugs often tag along: forgetting the `data:image/...;base64,` prefix (sending raw base64 characters alone), and labeling the wrong MIME type, such as `image/png` on a JPEG file. Let `mimetypes.guess_type` infer the MIME type from the filename extension as shown in the second code cell.
:::

:::caution[Knocking on the wrong door: asking a chat model to generate images, or sending images to a text-only model]
Asking questions about an existing image goes through `chat.completions` with a vision-capable `LLM_MODEL`. Creating a new image goes through `images.generate` with `IMAGE_MODEL`. Asking a chat model to "draw a picture" will only give you a text description, and sending an image to a text-only model will either fail with a 400 error or produce a hallucinated answer. Also remember that not every provider offers `images.generate`: as of 10/2026, Groq and Ollama do not expose it on their OpenAI-compatible endpoints.
:::

:::caution[Assuming "no error" means a parameter worked, or retrying a moderation refusal]
Two opposite habits that both cause trouble. Gemini's compatibility layer silently ignores any `images.generate` parameter outside its supported list, so passing `output_format="webp"` raises no error yet has zero effect—always check the supported parameter list when switching providers. Conversely, a content moderation refusal (`moderation_blocked`) will not clear up on its own if you retry: edit the prompt first. Automatic retry loops belong only on transient errors like 429 or 5xx, which the SDK already handles for you. Apply the same discipline when polling video jobs: use backoff and a maximum timeout rather than hammering the server.
:::

## Summary and further reading

**Key takeaways:**

- Asking about an image is still chat: the `user` message's `content` becomes a list of `text` and `image_url` parts. Its `url` field accepts either a web URL or a `data:<MIME>;base64,...` data URL, with data URLs working across the widest range of providers. Base64 adds roughly $1/3$ to the byte size, and images also consume model tokens.
- Generating an image uses the separate `images.generate` endpoint with `IMAGE_MODEL`. Read `response.data[0].b64_json`, decode it with `base64.b64decode`, and write the bytes to disk—while also checking `url` in case a provider returns a temporary link. Provider support and extra parameters vary.
- Video generation is an asynchronous job: submit the request, record the job `id`, poll with backoff and a timeout (or use a webhook), and copy the finished file to your own storage before the temporary link expires. Because video APIs change rapidly (10/2026), focus on this architectural pattern.
- Moderation refusals do not resolve by retrying unchanged prompts. Review provider terms before commercial use, disclose AI-generated media, and remember that C2PA metadata and watermarks help track provenance—but a missing marker never proves an image is real, and a present marker never proves its contents are factual.
